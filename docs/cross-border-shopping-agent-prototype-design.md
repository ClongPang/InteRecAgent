**版本**：2.0
**日期**：2026-08-15
**项目**：InteRecAgent
**工作名称**：跨境选物台
**适用端**：PC Web
**文档性质**：产品定位、交互原型和信息架构设计
**需求质量评分**：97/100

## 1. 设计结论

### 1.1 最终产品定位

InteRecAgent 不是普通的聊天机器人，也不是单纯的价格比较网站，而是一个：

> 以人民币预算为核心、聚合多个国际平台、通过持续对话帮助用户完成购买决策的购物任务 Agent。

它的核心交互不是“输入一次，返回一次结果”，而是：

```text
用户表达目标
  → Agent 复述理解并澄清一个关键问题
  → 用户补充或修正条件
  → Agent 检索、解释过程并更新结果工作区
  → 用户继续追问、筛选或比较
  → Agent 基于当前任务上下文给出可执行决定
```

因此，页面必须让用户同时看见两件事：

- **对话轨道**：Agent 当前理解了什么、正在做什么、为什么这样推荐、下一步可以怎么操作。
- **结果工作区**：候选商品、人民币价格、原币种、规格、价格历史和比较证据。

产品的最小价值闭环是：

```text
表达购物目标
  → Agent 澄清关键条件
  → 聚合国际平台候选商品
  → 统一换算人民币并比较
  → 形成候选清单
  → 给出有证据的推荐结论
  → 跳转商户购买或设置价格监控
```

### 1.2 核心设计原则

1. **任务优先**：用户进入的是一个购物任务，不是无限聊天。
2. **对话驱动任务，结构化信息承载证据**：对话用于理解、追问、控制筛选和解释；结果工作区用于浏览、比较和决策。
3. **渐进式披露**：先给少量可行动结果，再展开规格、价格历史和证据。
4. **人民币作为决策货币**：主展示人民币估算价，同时保留原币种、汇率和时间。
5. **证据优先**：每个推荐结论都能回溯到商品字段、平台和更新时间。
6. **不伪造跨境能力**：配送、税费、售后和最终到手价没有数据时，明确显示未知。
7. **让 Agent 做决策工作**：不是把 BuyWhere 的结果换一种语言展示，而是帮助用户缩小选择并解释取舍。
8. **每轮对话都产生状态变化**：用户的自然语言或快捷选项必须能更新任务约束、候选排序、比较范围或监控目标。
9. **对话可追溯**：用户可以回看 Agent 的理解、检索范围、推荐依据和未确认风险。

## 2. BuyWhere 能力复核

### 2.1 可直接用于原型的能力

BuyWhere 的公开 REST/MCP 能力包括商品搜索、商品详情、商品比较、折扣发现、分类浏览和价格历史。[BuyWhere MCP 集成指南](https://api.buywhere.ai/docs/guides/mcp)

| BuyWhere 能力 | 主要接口或工具 | 原型用途 |
|---|---|---|
| 商品搜索 | `GET /v1/products/search` / `search_products` | 发现页、搜索结果、候选池 |
| 商品详情 | `GET /v1/products/{id}` / `get_product` | 商品详情页、详情抽屉 |
| 商品比较 | `GET /v1/products/compare` / `compare_products` | 候选比较页 |
| 折扣发现 | `GET /v1/products/deals` / `get_deals` | 折扣发现页 |
| 最低价查询 | `find_best_price` | 已知商品的最低价任务 |
| 价格历史 | `GET /v1/products/{id}/prices` | 价格趋势和是否值得等待 |
| 分类浏览 | `/v1/categories` / `list_categories` | 探索型购物入口 |

### 2.2 商品卡片可直接读取的字段

BuyWhere 的公开文档和 MCP 示例提供了 `id`、`title`、`description`、`brand`、`domain`、`url`、`image_url`、`price`、`original_price`、`discount_pct`、`currency`、`country_code`、`rating`、`review_count`、`category_path`、`structured_specs`、`comparison_attributes`、`availability` 和 `updated_at` 等商品字段。正式接入以当前在线 OpenAPI 和真实 API 响应为准。[BuyWhere 在线 OpenAPI](https://api.buywhere.ai/openapi.json)

因此，第一版商品卡片可以真实展示：

- 商品图片、名称、品牌和型号
- 商品所在平台和国家
- 原始价格、原价、折扣和原始货币
- 人民币估算价格
- 评分和评价数量
- 关键商品规格
- 库存状态
- 商品数据更新时间
- 商户购买链接

### 2.3 必须由 InteRecAgent 自己计算的字段

以下不是 BuyWhere 原始事实，而是产品决策层：

- 人民币估算价
- 人民币价格排序
- 同款或近似款分组
- 预算匹配度
- 规格匹配度
- 综合推荐分
- 价格竞争力
- 数据新鲜度评分
- “适合你”的解释
- 是否值得现在购买

BuyWhere 明确说明商品价格以原生货币返回，API 不动态转换价格；`normalized_price_usd` 只是静态汇率下的粗略排序值，不适合直接作为用户价格展示。[官方 MCP 文档](https://api.buywhere.ai/docs/guides/mcp)

当前在线 OpenAPI 还支持 `mode=keyword|semantic|hybrid`：关键词模式适合精确型号，语义模式适合自然语言探索，混合模式适合默认搜索；语义基础设施不可用时会回退到关键词路径。原型不向用户暴露“搜索模式”这个技术选项，由 Agent 根据任务类型自动选择：精确型号使用 `keyword`，探索型需求使用 `hybrid`，模糊场景可尝试 `semantic`。

### 2.4 原型中不能假设为已知的信息

第一版不应把以下内容设计成确定字段：

- 最终运费
- 关税和清关费用
- 中国大陆配送可用性
- 准确配送时效
- 退货政策
- 保修政策
- 商户可信度
- 商品评论文本和评论质量
- 优惠券后的最终支付价
- 最终到手价

BuyWhere 的插件清单出现了 `deliver_to` 和 `local / ships_to_you / unavailable` 等位置感知字段，但当前公开 OpenAPI 商品结构主要明确的是库存状态。因此原型必须把“库存状态”和“配送可用性”分成两个字段；真实接口未确认前，配送状态显示“待确认”。[BuyWhere 插件清单](https://api.buywhere.ai/.well-known/ai-plugin.json)

## 3. 产品经理与原型设计视角的讨论

### 3.1 讨论一：产品应该是聊天页，还是商品页？

**产品经理视角：**

用户需要自然地说出复杂需求，聊天是最低门槛的入口；Agent 也需要通过追问获得预算、用途和配送目的地。

**原型设计视角：**

纯聊天无法承载多平台商品、规格和价格的横向比较。用户在做购买决策时需要扫描、排序、选择和回看证据，而不是阅读一长段回复。

**共同结论：**

采用“对话主控区 + 结果工作区”的组合，而不是把对话降级成一条结果摘要：

- 对话主控区负责需求理解、关键追问、检索进度、筛选控制和推荐解释。
- 结果工作区承载商品卡片、人民币价格、规格和比较表，随对话状态实时更新。
- Agent 的每条关键消息至少提供一个动作或结果引用，例如“只看有货”“比较这两件”“查看推荐依据”。
- 用户可以直接在对话中修改预算、平台、用途和排序，不需要重新创建任务。

### 3.2 讨论二：是否一直保持三栏布局？

**产品经理视角：**

固定三栏可以同时放筛选、结果和 Agent 建议，看起来功能完整。

**原型设计视角：**

固定三栏会造成持续的信息竞争：左侧筛选、中间商品、右侧聊天都在争夺注意力；用户还没有开始比较时，比较面板是噪音。

**共同结论：**

不使用永久三栏，也不把对话藏到偶发的右侧抽屉。PC 端默认使用非对称双栏：左侧固定对话主控区，右侧为可变结果工作区；在比较阶段，左侧可以收窄，但仍保留“继续追问 Agent”的入口。

| 阶段 | 主布局 |
|---|---|
| 创建任务 | 居中首轮输入，创建后进入任务会话 |
| 澄清需求 | 对话主控区 + 购物简报卡 |
| 发现候选 | 对话主控区 + 候选结果工作区 |
| 比较商品 | 收窄对话区 + 全宽比较表 + 决策摘要 |
| 查看详情 | 详情抽屉覆盖结果区，对话保留任务上下文 |
| 价格监控 | 监控列表 + 可追问的价格任务会话 |

布局约束：对话区宽度 320–380px，结果区占剩余空间；不得让两个区域等宽，避免页面看起来像普通 IM 软件。

### 3.3 讨论三：是否突出“最低人民币价格”？

**产品经理视角：**

人民币最低价容易理解，能够提高点击商户链接的概率。

**原型设计视角：**

最低商品价可能不包含运费、税费，也可能是不同型号、翻新机或库存有限商品；突出最低价会损害信任。

**共同结论：**

页面必须区分：

- 最低商品价
- 综合推荐
- 规格最匹配
- 平台信息最完整
- 已知总价最低

“最低价”只是一个排序选项，不能成为默认推荐结论。

### 3.4 讨论四：Agent 是否应该自动替用户做决定？

**产品经理视角：**

产品价值是缩短决策时间，必须给出明确的首选项。

**原型设计视角：**

跨境商品信息存在缺失和价格波动，直接使用“你应该买 A”可能造成过度承诺。

**共同结论：**

Agent 可以给出明确推荐，但必须同时展示：

- 推荐依据
- 主要取舍
- 数据更新时间
- 未确认的信息
- 备选商品

推荐表达使用“基于当前信息，更适合你的选择是 A”，而不是“绝对最优”或“全网最低”。

### 3.5 讨论五：对话是不是只放一个输入框？

**产品经理视角：**

如果只有首屏输入框，用户完成第一次搜索后就会回到传统商品列表；Agent 无法承接“为什么推荐”“更便宜一点”“只看能直邮的”等连续意图，复购和任务完成率都会下降。

**原型设计视角：**

对话不能只是聊天气泡。它需要成为可观察、可操作的任务轨道：每轮消息都应说明 Agent 的当前判断或进展，并提供能改变结果的快捷动作；商品卡片和比较表则作为消息引用的结构化结果。

**共同结论：**

对话区必须具备五类消息：

1. **理解消息**：复述商品、预算、用途、目的地等当前约束。
2. **澄清消息**：一次只问一个会改变排序的关键问题，并给出选项。
3. **工具进度消息**：说明正在搜索哪些平台、整理哪些字段、换算哪种货币。
4. **结果消息**：总结候选数量、差异和下一步操作，并引用右侧结果。
5. **决策消息**：给出推荐、主要取舍、风险和可执行动作。

消息底部统一使用动作 Chips，例如：`只看有货`、`预算改为 ¥2000`、`比较前 3 个`、`为什么推荐它`。用户点击动作和输入自然语言，使用同一个任务状态更新通道。

## 4. 对话式 Agent 定位

### 4.1 Agent 的核心对象：Shopping Mission

产品不应只保存一段聊天记录，而应保存一个可持续推进的购物任务：

```text
ShoppingMission
├── 用户目标
├── 商品类别或具体型号
├── 人民币预算
├── 比较货币
├── 商品市场
├── 配送目的地
├── 平台范围
├── 硬性约束
├── 偏好约束
├── 候选商品
├── 推荐结论
├── 商户跳转记录
└── 价格监控状态
```

### 4.2 Agent 任务类型

首次输入后，Agent 先判断任务类型，而不是直接调用搜索：

| 任务类型 | 用户表达 | Agent 目标 | 主要页面 |
|---|---|---|---|
| 探索型推荐 | “我想买一台适合剪辑的电脑” | 找到不同取向的候选方案 | 发现页 |
| 明确商品比价 | “比较 iPhone 16 Pro 在几个平台的价格” | 识别同款并比价 | 比较页 |
| 最低价查询 | “这个耳机哪里最便宜” | 找当前可用的低价报价 | 报价页 |
| 候选决策 | “Sony 和 Bose 选哪个” | 按场景给出取舍 | 决策页 |
| 折扣探索 | “找最近值得买的显示器” | 发现折扣和价值候选 | 折扣页 |
| 价格监控 | “降到 1500 元提醒我” | 建立持续任务 | 监控页 |

### 4.3 任务状态机

```text
DRAFT
  ↓
CLARIFYING
  ↓
DISCOVERING
  ↓
SHORTLIST_READY
  ↓
COMPARING
  ↓
DECISION_READY
  ↓
HANDOFF
  ↓
MONITORING / COMPLETED
```

每个状态只展示当前最重要的下一步，不把所有能力同时暴露给用户。

### 4.4 对话状态模型

对话不是独立的聊天记录，而是任务状态的可读投影。每轮消息都应带上消息类型、影响范围和可执行动作：

```json
{
  "message_type": "clarification | progress | result | decision | user",
  "text": "你更在意降噪效果还是续航？",
  "mission_delta": {
    "preference": "battery_life"
  },
  "references": ["sony-xm5", "sennheiser-m4"],
  "actions": [
    { "label": "更在意降噪", "command": "偏好降噪" },
    { "label": "更在意续航", "command": "偏好续航" }
  ],
  "evidence": {
    "source": "BuyWhere",
    "updated_at": "2026-08-15T14:32:00+08:00"
  }
}
```

前端不需要暴露 JSON 或技术字段，但要把它们映射为可理解的消息、引用卡、动作 Chips 和任务摘要。用户可以点击动作，也可以直接输入同义自然语言；两者必须更新同一个 `ShoppingMission`。

### 4.5 一轮对话的产品契约

一轮 Agent 输出遵循“理解 → 行动 → 结果 → 下一步”的短结构：

```text
我理解你要找：通勤用降噪耳机，预算 ¥2500，送至中国大陆。
我正在搜索 Amazon US、Lazada SG 和 Best Buy US，并把价格换算为 RMB。
目前找到 12 个候选，右侧先展示 3 个取向不同的选择。
[只看有货] [优先续航] [比较前 3 个]
```

当无法继续时，Agent 必须说明卡在哪里，并给出恢复动作；禁止只显示“加载失败”或把用户踢回首页。

## 5. PC Web 信息架构

### 5.1 顶层导航

```text
跨境选物台

新建购物任务    我的任务    候选清单    价格监控

右侧：比较货币 RMB  · 配送目的地  · 账户
```

顶部的“比较货币”和“配送目的地”必须分开：

- 比较货币：默认 RMB。
- 配送目的地：例如中国大陆、新加坡、美国。

人民币只表示比较方式，不代表商品支持配送到中国大陆。

### 5.2 页面和路由

| 路由 | 页面 | 目标 |
|---|---|---|
| `/` | 任务首页 | 创建新的购物任务 |
| `/missions/:id` | 购物任务工作台 | 查看任务阶段、候选和 Agent 进度 |
| `/missions/:id/discover` | 候选发现页 | 浏览和筛选跨平台商品 |
| `/missions/:id/compare` | 比较决策页 | 选择候选并获得推荐 |
| `/products/:id` | 商品详情页 | 查看商品、规格和价格历史 |
| `/watchlist` | 价格监控页 | 管理目标商品和价格提醒 |

### 5.3 任务工作台布局

`/missions/:id` 是对话式 Agent 的主场，不是单纯的结果列表：

```text
┌──────────────────────────────────────────────────────────────────┐
│ 任务阶段轨道 · 购物简报 → 候选池 → 比较决策 → 去购买               │
├──────────────────────┬───────────────────────────────────────────┤
│ 对话主控区 320–380px  │ 结果工作区                               │
│                      │                                           │
│ 任务摘要              │ Agent 结果摘要 / 汇率信号                  │
│ 用户消息              │ 筛选与排序                                │
│ Agent 理解            │ 商品卡片 / 比较表 / 详情                   │
│ 澄清选项              │                                           │
│ 检索进度              │                                           │
│ 推荐与依据            │                                           │
│                      │                                           │
│ [输入追问……] [发送]   │                                           │
└──────────────────────┴───────────────────────────────────────────┘
```

对话区使用固定宽度和独立滚动，结果区可以在发现、比较和详情三种工作模式间切换。对话区收起后，顶部必须显示“继续追问 Agent”按钮；用户不应失去上下文，也不应被迫重新开始任务。

## 6. 页面原型设计

### 6.1 首页：创建购物任务

#### 页面目标

让用户在 10 秒内表达购物目标，并让 Agent 从首轮对话开始建立可持续推进的购物任务。

#### 线框

```text
┌──────────────────────────────────────────────────────────────┐
│ 跨境选物台                                  RMB  · 配送地：中国大陆 │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                 先告诉我，你想买什么？                        │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 帮我找一副适合通勤的降噪耳机，预算 2500 元以内……       │  │
│  └────────────────────────────────────────────────────────┘  │
│                         [开始找]                              │
│                                                              │
│  你可以直接说：                                               │
│  [我不知道买什么] [帮我跨平台比价] [比较几个商品]              │
│  [找当前折扣] [设置价格提醒]                                  │
│                                                              │
│  最近的购物任务                                               │
│  耳机比较 · 笔记本选购 · 游戏显示器价格监控                   │
└──────────────────────────────────────────────────────────────┘
```

#### 组件

- 自然语言输入框
- 任务模式快捷入口
- 比较货币选择器
- 配送目的地选择器
- 最近购物任务
- 示例问题

#### 交互规则

- 输入框支持商品、用途、预算、平台和国家的混合表达。
- 首次提交后不留在首页，而是创建任务并进入带有对话历史的任务工作台。
- 用户只说“找耳机”时，Agent 先询问预算和使用场景，不直接返回大量结果。
- 用户明确说“哪里便宜”时，直接进入最低价模式。
- 用户粘贴商品 URL 时，进入已知商品比价模式；如果 BuyWhere 无法解析 URL，转为名称和型号搜索。

首页的输入框是对话的第一轮，不是产品的全部对话能力。提交后，输入框的文案应变为“继续告诉我你的偏好……”，并保留用户原话、Agent 复述和后续追问。

### 6.2 澄清阶段：购物简报

#### 页面目标

用最少的问题补齐影响排序的关键变量。

#### 线框

```text
┌──────────────────────────────┬───────────────────────────────┐
│ 对话主控区                    │ 购物简报                       │
│                              │                               │
│ 用户：通勤降噪耳机，预算2500 │ 商品：降噪耳机                  │
│                              │ 预算：¥2500 以内               │
│ Agent：你更在意哪一项？       │ 比较货币：RMB                  │
│ [通勤] [长途旅行] [办公]      │ 配送地：中国大陆                │
│ [游戏] [我不确定]             │ 平台：待选择                    │
│                              │ 用途：待确认                    │
│ Agent：是否接受翻新机？       │                               │
│ [接受] [只要全新] [不确定]     │ [修改预算] [选择平台]           │
│                              │                               │
│ [输入补充条件……] [发送]       │                               │
└──────────────────────────────┴───────────────────────────────┘
```

#### Agent 追问原则

- 每轮最多询问一个主要问题。
- 只询问会改变候选排序的问题。
- 提供“我不确定”选项。
- 用户不回答时，可以带着不完整条件搜索，但明确标记影响。
- 预算、目的地和商品型号属于高优先级；颜色等属性属于低优先级。

#### 购物简报状态

```text
已确认：商品、预算、用途、比较货币
待确认：配送目的地、平台偏好
缺失信息：运费和税费
```

### 6.3 候选发现页

#### 页面目标

让用户从大量结果快速得到 3–5 个有差异的候选，而不是浏览无尽商品列表。

#### 布局

```text
┌──────────────────────┬───────────────────────────────────────┐
│ 对话主控区            │ 候选结果工作区                         │
│                      │                                       │

│                      │ 预算 ¥2500 · 配送地：中国大陆           │

│                      │ 平台：全部 · 有货 · 折扣                │
│ [只看有货]            │                                       │
│ [优先续航]            │ Agent 结果引用：先比较 Sony、Bose、       │
│ [比较前 3 个]         │ Sennheiser，右侧展示不同取向的候选。     │

│ 还是续航？            │ Amazon · US · 约 ¥2149 · USD 299        │
```

发现页的 Agent 消息必须引用右侧候选，而不是另起一段无法操作的摘要。用户点击“优先续航”后，结果区更新排序，同时对话区追加一条“已按续航重新排序”的确认消息。

#### 商品卡片字段优先级

**第一层：用户必须一眼看到**

- 商品名称
- 平台和国家
- 人民币估算价
- 原始价格
- 关键推荐标签
- 加入候选按钮

**第二层：帮助用户判断**

- 品牌和型号
- 评分和评价数量
- 2–4 个关键规格
- 库存状态
- 折扣比例

**第三层：证据和风险**

- 数据更新时间
- 汇率时间
- 是否包含运费和税费
- 配送信息状态
- 原始购买链接

#### 推荐标签

标签必须表达排序依据，不使用夸张营销语：

- 综合最优
- 人民币价格最低
- 规格最匹配
- 评分信息较完整
- 当前折扣较高
- 数据较新
- 信息不完整

### 6.4 候选清单

候选清单是从发现到决策的中间层，建议最多保留 5 个商品。

```text
已选 3 件商品

┌──────────┬──────────┬──────────┐
│ 商品 A    │ 商品 B    │ 商品 C    │
│ 约 ¥2149  │ 约 ¥1969  │ 约 ¥2380  │
│ Amazon   │ Lazada   │ Best Buy │
└──────────┴──────────┴──────────┘

[开始比较] [移除不合适商品] [继续找更多]
```

当候选不足 2 个时，“开始比较”按钮不可用，但可以继续搜索；当候选超过 5 个时，引导用户先删除或让 Agent 筛选。

#### 页面目标

让用户回答“我应该买哪一个”，而不是只看到规格差异。

#### 比较表设计规则

- 默认只显示会影响决策的字段。
- 相同规格合并为一行，不同规格高亮。
- 缺失信息显示“未知”或“未提供”，不能显示空白。
- 原始货币和人民币估算价必须同时展示。
- 每个价格显示汇率时间或统一放在表头说明。
- 跨币种价格只能作为估算比较，不能显示成最终支付金额。
- 比较页顶部必须有 AI 结论，但用户可以展开依据。

## 8. 人民币价格展示规范

### 8.1 标准价格组件

```text
约 ¥2,149
USD 299
汇率更新时间：2026-08-15 10:30
商品价，不含运费和税费
```

### 8.2 价格状态

| 状态 | 展示方式 |
|---|---|
| 有实时汇率 | `约 ¥2,149`，显示汇率时间 |
| 使用缓存汇率 | `约 ¥2,149`，显示“汇率缓存于 X 小时前” |
| 汇率服务异常 | 显示原币种，人民币价格标记“暂无法换算” |
| 有运费但无税费 | 显示“已含已知运费，税费未知” |
| 所有额外费用未知 | 显示“商品价估算，不等于到手价” |

### 8.3 禁止用语

- “绝对最低价”
- “最终到手价”——没有完整费用数据时
- “保证可配送”——没有配送数据时
- “官方正品”——没有商户认证数据时
- “实时价格”——数据更新时间不明确时

## 9. Agent 交互规范

### 9.1 Agent 输出结构

每次搜索或推荐响应都按以下顺序组织：

1. 当前理解的购物目标
2. 已确认的约束
3. 缺失但重要的信息
4. 已执行的搜索范围
5. 候选结果
6. 推荐结论
7. 主要取舍
8. 数据和价格风险
9. 下一步行动

### 9.1.1 对话消息规范

| 消息类型 | 用户看到的内容 | 必须提供的动作或证据 |
|---|---|---|
| 用户消息 | 用户原话和已提交的筛选条件 | 可编辑或撤回最近一次条件 |
| 理解消息 | Agent 对商品、预算、用途和目的地的复述 | 修改约束、确认并继续 |
| 澄清消息 | 一个关键问题和 2–4 个选择 | 快捷回答、我不确定 |
| 进度消息 | 正在搜索的平台、同款整理和 RMB 换算进度 | 查看检索范围、停止当前任务 |
| 结果消息 | 候选数量、差异和右侧结果引用 | 只看有货、排序、加入候选 |
| 决策消息 | 推荐、取舍、风险和下一步 | 查看依据、比较商品、去商户 |
| 系统消息 | API 限流、汇率异常或数据缺失 | 重试、缩小范围、保留当前结果 |

### 9.1.2 对话输入区

输入区固定在对话主控区底部，包含：

- 多行输入框，placeholder 为“继续告诉我你的偏好……”；
- 发送按钮，Enter 发送，Shift + Enter 换行；
- 最近一次条件的可撤销标签；
- 当 Agent 正在搜索时，按钮变为“停止搜索”；
- 允许用户输入自然语言，不要求暴露 BuyWhere 的 `mode`、`domain` 或币种参数。

输入区上方保留 2–4 个上下文相关动作，不能永久展示一堆通用功能。动作顺序应该来自当前任务的下一步，例如澄清阶段显示“通勤 / 长途 / 办公”，候选阶段显示“只看有货 / 比较前 3 个”。

### 9.2 Agent 可执行动作

用户可以直接说：

- “只看 Amazon 和 Best Buy。”
- “把预算改成 2000 元。”
- “只要有货的。”
- “排除翻新机。”
- “比较前面三个。”
- “为什么不推荐第二个？”
- “只看人民币价格最低的。”
- “降到 1500 元提醒我。”

Agent 应把这些自然语言转成任务状态或筛选条件，而不是重新开始一个无关的对话。

前端交互要求：

- 点击消息动作后，先在对话区追加用户消息，再更新右侧结果区，避免用户不知道动作是否生效。
- 用户点击商品卡片中的“加入候选”时，在对话中留下轻量事件记录，不打断浏览。
- 用户在比较页继续追问时，保留比较表，新增的 Agent 决策只更新摘要和高亮，不清空候选。
- 用户关闭详情抽屉后，回到原来的对话滚动位置和结果滚动位置。

### 9.3 追问优先级

优先询问：

1. 商品类别或型号
2. 人民币预算
3. 配送目的地
4. 使用场景
5. 必须满足的规格
6. 平台偏好
7. 颜色等低影响属性

### 9.4 Agent 不确定性表达

推荐理由必须区分：

- **已验证**：来自 BuyWhere 字段。
- **计算得出**：人民币换算、排序和匹配分。
- **未确认**：配送、税费、售后或商户信息。

推荐文案示例：

> 基于当前商品价格、规格和评分，A 是更符合你需求的选择。人民币价格是按当前汇率计算的商品价估算，不包含可能的运费和税费；配送到中国大陆的可行性需要在商户页面确认。

## 10. 页面状态和异常设计

### 10.1 加载状态

加载时要告诉用户 Agent 正在做什么：

```text
正在搜索 5 个目标平台
正在整理同款规格
正在换算人民币价格
正在生成候选方案
```

不要只显示一个旋转图标。

### 10.2 无结果

```text
没有找到同时满足所有条件的商品。

当前保留的硬条件：预算 ¥2500、支持降噪
可能导致无结果的条件：指定平台、配送地中国大陆

[放宽平台范围] [提高预算] [继续保留硬条件]
```

Agent 不得静默放宽用户的硬约束。

### 10.3 API 限流或失败

```text
部分平台暂时无法查询。

已返回 3 个可用平台的结果，以下商品可能不完整。
你可以稍后重试，或继续比较当前结果。
```

### 10.4 信息不完整

使用明确标签：

- 未提供
- 待确认
- 商品价估算
- 非实时汇率
- 库存信息可能过期
- 不包含运费税费

不要使用空白字段，因为空白会被用户误解为系统遗漏。

## 11. 视觉和交互方向

### 11.1 设计主题

视觉主题定为“跨境购物情报台”，而不是传统商城。

设计气质：

- 明确
- 克制
- 有证据感
- 适合长时间比较
- 突出人民币价格和数据时间

### 11.2 色彩建议

| 用途 | 颜色 |
|---|---|
| 页面背景 | `#F7F8FA` |
| 主文字 | `#18212F` |
| 次文字 | `#64748B` |
| 主操作色 | `#2457D6` |
| 人民币价格强调 | `#B45309` |
| 满足条件 | `#15803D` |
| 信息未知 | `#A16207` |
| 风险提示 | `#B91C1C` |
| 边框 | `#E2E8F0` |

价格强调使用深琥珀色，而不是大面积红色，避免把所有价格都做成促销广告。

### 11.3 排版和组件

- 页面标题使用中文无衬线字体，保持清晰和紧凑。
- 价格使用较大字号，但原币种和汇率说明使用小字号。
- 表格行高要足够，方便扫描规格。
- 证据、时间和状态使用小型标签。
- 卡片圆角适中，不使用过度圆润的“聊天 App”风格。
- 主按钮使用动作词：`加入候选`、`开始比较`、`查看详情`、`去商户`。

### 11.4 对话组件设计系统

#### ConversationPanel

| 属性 | 规则 |
|---|---|
| 默认宽度 | 320–380px，独立滚动，不与结果区等宽 |
| 结构 | 任务摘要 → 消息时间线 → 上下文动作 → 输入区 |
| 变体 | `default` 发现模式；`compact` 比较模式；`collapsed` 收起模式 |
| 消息类型 | `user`、`understanding`、`clarification`、`progress`、`result`、`decision`、`system` |
| 输入状态 | 默认、输入中、发送中、Agent 检索中、失败可重试 |
| 关键动作 | Enter 发送；Shift + Enter 换行；Esc 关闭详情或取消当前操作 |

#### MessageActionChip

- 默认状态使用浅蓝底和细边框，表示“会改变任务结果”的可选动作。
- Hover/Focus 状态提高对比度，不依赖颜色单独传达状态。
- Disabled 状态说明不可用原因，例如“需要至少选择 2 个候选”。
- 每个 Chip 必须使用用户能理解的动作词，不显示内部工具名或 API 参数。

#### 可访问性

- 对话时间线使用 `aria-live="polite"`，新 Agent 消息不会打断屏幕阅读器当前朗读。
- 输入区使用明确的 `aria-label`；发送按钮在空输入时禁用并保留可见焦点样式。
- 所有动作 Chips、收起/展开、详情抽屉和取消动作均支持键盘 Tab、Enter 和 Escape。
- 加载状态同时提供文字进度，不只依靠动画；系统尊重 `prefers-reduced-motion`。

## 13. 原型验收标准

### 产品验收

- 用户能从一句自然语言创建购物任务。
- Agent 能识别探索、比价、最低价、候选决策和价格监控任务。
- 用户能看到至少 3 个来源平台或市场的候选结果，前提是 BuyWhere 实际返回覆盖。
- 用户能用人民币预算筛选和排序。
- 用户能看到原价、人民币估算价、汇率时间和价格说明。
- 用户能选择 2–5 个商品并完成横向比较。
- Agent 能给出首选、备选和主要取舍。
- 用户能从推荐结果跳转至真实商户链接。

### 信任验收

- 每个价格都标明原币种或人民币换算状态。
- 每个商品都显示数据更新时间。
- 缺失配送、税费和售后信息时，页面显示明确的未知状态。
- 任何推荐结论都能回溯到商品字段或计算规则。
- API 失败时页面不展示伪造的商品结果。

### 交互验收

- 用户不需要学习 API 参数即可完成搜索。
- 用户提交首轮需求后，能在同一任务工作台看到对话历史，而不是只看到一条 Agent 摘要。
- Agent 每轮输出都能看出当前理解、正在执行的动作或下一步建议。
- 用户可以通过自然语言或动作 Chips 修改预算、用途、平台和排序，右侧结果会同步变化。
- 用户可以看到“正在搜索哪些平台”“正在换算人民币”等进度消息。
- 对话消息可以引用商品、比较结果和推荐依据，点击引用能定位到右侧工作区。
- Agent 每轮最多询问一个关键问题。
- 用户可以修改预算、平台和用途，而不用重新创建任务。
- 用户可以从发现页进入比较页，再返回候选清单。
- 页面不会在用户没有选择商品时强行展示复杂比较表。

## 14. 埋点和业务指标

### 任务漏斗

```text
创建购物任务
  → 完成需求澄清
  → 看到候选结果
  → 加入候选
  → 开始比较
  → 查看推荐依据
  → 点击商户链接
  → 保存或设置监控
```

### 关键指标

- 任务创建到首次候选结果的完成率
- 平均澄清轮数
- 候选加入率
- 比较启动率
- 推荐依据展开率
- 商户链接点击率
- 价格监控设置率
- 用户修改推荐条件的比例
- 人民币价格换算失败率
- API 数据缺失率
- 推荐后用户继续追问的比例

### 业务判断

本产品早期不应只看页面停留时间。更重要的是用户是否完成了“从需求到可执行购买选择”的过程。

## 15. 开发依赖与验证清单

1. 用真实 BuyWhere API Key 验证搜索结果是否使用 `data` 还是其他字段，并在 Adapter 中统一。
2. 验证实际可用的平台、国家和商品覆盖，不以营销页面的数量作为产品承诺。
3. 验证 `mode=keyword`、`mode=semantic` 和 `mode=hybrid` 的实际效果、耗时和回退行为。
4. 验证商品 ID 是否能稳定用于详情、比较和价格历史接口。
5. 验证 `availability` 只表示库存，还是同时包含配送状态。
6. 继续核对 `deliver_to` 是否在当前实际接口中可用。
7. 接入独立汇率服务，并为人民币换算保存汇率时间和来源。
8. 验证价格历史的时间跨度、更新频率和跨币种计算方式。
9. 确认购买链接、归因规则和商业使用许可。
10. 用至少 30 个真实购物问题进行原型可用性测试。
11. 对“找商品”“跨平台比价”“候选决策”“设置价格提醒”分别建立评估集。

## 16. 最终设计摘要

InteRecAgent 的 PC Web 原型采用“对话驱动的购物任务工作台”，而不是静态比价页或普通聊天页，也不是固定三栏布局：

- 首页让用户创建任务。
- 任务工作台保留完整对话时间线，让 Agent 复述理解、澄清条件、反馈检索进度并解释结果。
- 右侧结果工作区展示少量有差异的候选方案，并被对话动作实时驱动。
- 澄清阶段让 Agent 逐步补齐关键约束，每轮只问一个高价值问题。
- 候选清单承接用户选择。
- 比较页提供全宽结构化对比和 AI 决策摘要。
- 详情页展示商品事实、规格和价格历史。
- 价格监控页承接持续任务，并允许用户继续追问目标价和等待时机。

对话是任务控制面，结构化商品数据是证据面，AI 决策摘要是价值输出，商户跳转是业务闭环。

产品是否“对话式”的判断标准不是页面上有没有一个聊天输入框，而是：用户的每轮表达是否都能被 Agent 理解、反馈并转化为任务状态或结果变化。

这个产品真正要完成的不是“帮用户搜索更多商品”，而是：

> 在多个国际平台、不同原始货币和不完整跨境信息中，帮助用户用人民币预算做出一个有依据、可执行、知道风险的购买选择。
