# 跨平台跨境 AI 商品推荐 Agent 产品需求文档

**版本**：1.1
**日期**：2026-08-15
**项目**：InteRecAgent
**文档类型**：产品需求与 Agent 架构基线
**需求质量评分**：94/100

## 1. 产品概述

### 1.1 产品定位

InteRecAgent 是一个面向中文跨境消费者的、可追踪且可解释的跨平台 AI 商品推荐 Agent。

它将用户的自然语言购物需求转化为可验证的商品约束，从多个国际电商平台和国家市场中检索商品，统一换算为人民币进行横向比较，并输出带有事实依据、取舍说明和商户链接的推荐结果。

产品首期不定位为自动代购或自动下单系统，而定位为“跨平台跨境购物研究员”和“商品购买决策助手”。

### 1.2 平台聚合与首期策略

首期不绑定单一国家或单一平台，而是以 BuyWhere 实际可用的国际平台和国家市场为数据边界，服务以人民币进行决策的中文用户。优先覆盖 3C 数码、家居电器、美妆个护和游戏娱乐设备。

原因如下：

- 用户真正需要的是“一次搜索、多个平台比较”，而不是逐个平台打开网页。
- 人民币是目标用户的统一决策货币，但商品价格仍必须保留原币种和汇率信息。
- 首期应选择 2–3 个可稳定调用的市场和平台进行验证，再逐步扩展覆盖范围。

BuyWhere 的公开资料覆盖新加坡、美国及部分东南亚市场，但公开页面的覆盖数量和接口字段存在差异；具体市场应以真实 API Key 的可用结果为准。

“人民币”只表示用户的比较和预算货币，不代表商品一定可以配送到中国大陆。系统必须将“比较货币”“商品所在市场”和“配送目的地”作为三个独立字段处理。

## 2. 背景与问题

### 2.1 用户现状

跨境购物用户通常需要在多个国际平台之间手动搜索、翻译和比价，同时处理不同的币种、商品规格、促销价格、商户信誉、库存状态和售后规则。

传统搜索只能提供商品列表，无法有效回答以下问题：

- 以人民币预算计算，哪个商品最适合？
- 不同平台的商品是否真的是同款？
- 不同国家的价格换算成人民币后，哪个平台更划算？
- 低价是否意味着规格缩水、套装不同或售后较差？
- 当前价格是否值得购买，还是应该等待降价？
- 价格、库存和评分信息是什么时间更新的？

### 2.2 产品机会

BuyWhere 提供面向 AI Agent 的商品目录、结构化规格、商户信息、价格、库存、折扣和比较接口，能够替代 Agent 对网页抓取、页面解析和静态知识的依赖。

BuyWhere 的核心 REST API 为 `https://api.buywhere.ai/v1`，同时提供 MCP 接入。搜索接口支持关键词、平台、区域、国家、价格区间、货币、分页和紧凑响应模式；商品结果包含 `structured_specs` 与 `comparison_attributes`，适合进一步进行程序化比较。[BuyWhere OpenAPI 规范](https://raw.githubusercontent.com/api-evangelist/buywhere/refs/heads/main/openapi/buywhere-openapi.yml)

## 3. 产品目标与非目标

### 3.1 产品目标

1. 让用户用一句自然语言表达购物需求，并通过少量追问补齐关键约束。
2. 在多个国际平台和市场之间找到满足硬条件的候选商品。
3. 将不同平台的原币种价格换算为人民币，支持统一预算和横向比价。
4. 通过结构化数据完成可解释的商品比较，而不是只返回搜索结果。
5. 为每个推荐结论保留原价、人民币估算价、汇率时间、规格、商户、库存和更新时间等证据。
6. 在 BuyWhere API 不可用、数据不完整或信息过期时，明确告知用户不确定性。

### 3.2 非目标

- MVP 不负责自动支付、自动下单或代替用户完成交易。
- MVP 不承诺最终运费、关税、清关费用或配送时效；人民币价格默认是商品价换算，不等于跨境到手价。
- MVP 不对商户的真实性、售后质量或保修政策做无依据的保证。
- MVP 不声称“全网最低价”，只能表述为“在当前可检索结果中的较优选择”。
- MVP 不构建自有商品爬虫和完整电商目录。

## 4. 目标用户

### 4.1 主要用户：跨境理性消费者

- **典型特征**：以人民币进行预算管理，会使用中文，熟悉部分电商平台，但没有时间逐个平台比价。
- **目标**：在预算内买到合适、可靠、值得购买的商品。
- **痛点**：国际平台分散、商品规格不统一、跨币种比较困难、汇率波动、低价和真实价值不等价。
- **关键诉求**：人民币价格、原币种和汇率时间、推荐理由、候选差异、价格与库存更新时间、购买链接。

### 4.2 次要用户：高频选品用户

- **典型特征**：经常购买数码、家电或游戏设备，愿意保存偏好和监控价格。
- **目标**：建立个人偏好、关注商品降价和快速复用跨平台搜索条件。
- **关键诉求**：愿望清单、价格历史、人民币目标价、降价提醒和跨市场追踪。

## 5. 核心用户旅程

```text
用户提出购物目标
        ↓
Agent 识别商品、人民币预算、目标市场和硬约束
        ↓
对缺失条件进行最少量追问
        ↓
调用 BuyWhere 搜索候选商品
        ↓
规格归一化、同款识别、硬约束过滤
        ↓
换算人民币并比较价格、评分、库存、更新时间和商户
        ↓
输出首选、备选、取舍理由和购买链接
        ↓
用户继续追问、比较或跳转购买
```

示例：

> 我想买一副适合通勤的降噪耳机，人民币预算不超过 2,500 元，帮我比较美国、新加坡和东南亚平台。

Agent 应识别出：商品类别、使用场景、人民币价格上限、目标市场、降噪能力和可购买性，并在必要时追问是否接受翻新机、是否重视续航、品牌、运费或保修。

## 6. 功能需求

### 6.1 自然语言需求理解

系统需要从用户输入中提取：

- 商品类别或具体型号
- 使用场景
- 人民币预算和原始货币
- 目标国家、平台或配送地
- 品牌偏好或排除项
- 尺寸、颜色、容量、性能等规格
- 必须满足的硬条件
- 可接受的折中项

**要求：**

- 无法确定商品类别时，Agent 必须追问。
- 预算未提供时，可以先搜索，但应提醒用户结果未按人民币预算约束。
- 用户表达“便宜”“最好”“性价比高”等模糊目标时，系统应转化为可解释的排序策略。
- 用户修改一个约束时，只重新执行受影响的搜索和排序步骤。

### 6.2 BuyWhere 商品搜索

首期使用 `GET /v1/products/search`，按国家或平台分组检索候选商品，主要参数如下：

| 参数 | 用途 |
|---|---|
| `q` | 自然语言或关键词搜索 |
| `domain` | 商户平台过滤，例如 Shopee、Lazada、Amazon |
| `region` | 区域过滤 |
| `country_code` | 目标国家 |
| `min_price` / `max_price` | 对应市场原币种下的价格区间 |
| `currency` | 显式指定市场原币种；不默认传入 CNY |
| `compact` | 获取更适合 Agent 的精简响应 |
| `limit` / `offset` | 分页 |

系统应优先使用 `compact=true` 获取候选集，再按需要获取详情、比较或价格历史。

BuyWhere 的搜索价格过滤发生在目标市场的原币种中。用户输入人民币预算后，系统需要先使用汇率服务估算各市场的原币种预算，再分别调用搜索接口，不能直接假设 BuyWhere 接受人民币预算。

### 6.3 候选商品处理

系统必须在推荐前完成：

- 硬约束过滤
- 商品规格标准化
- 型号、容量、颜色和套装识别
- 同款或近似款区分
- 价格币种确认
- 库存和更新时间检查
- 商户及原始链接保留

不能仅按搜索结果顺序直接把第一项作为推荐。

### 6.4 跨平台人民币比价

系统必须提供统一的人民币展示层，同时保留商品原价。每个价格至少包含：

- 原始价格和原始货币，例如 `USD 299`、`SGD 429`。
- 按指定汇率换算后的人民币估算价，例如 `约 ¥2,149`。
- 汇率来源和更新时间。
- 是否包含已知运费、税费或平台费用。
- 价格换算置信度。

人民币换算价的定位是“比较价”，不是最终支付金额。默认展示格式应为“约 ¥X”，而不是伪装成精确人民币售价。

排序时应区分三种价格：

1. **商品人民币估算价**：原价 × 汇率。
2. **已知总价估算**：商品价 + 已知运费 + 已知税费。
3. **最终到手价**：只有在接入可靠物流、税费和平台费用数据后才能展示。

MVP 只承诺前两种，并明确标注数据缺失项。

### 6.5 商品比较

用户可以要求比较 2–10 个候选商品。比较维度至少包括：

- 当前原价、人民币估算价和汇率时间
- 品牌与型号
- 关键规格
- 评分和评价数量
- 折扣信息
- 库存状态
- 商户平台
- 数据更新时间

当商品跨越不同货币时，系统不得把 BuyWhere 的静态 `normalized_price_usd` 直接转换成用户最终支付价格。该字段只能作为粗略排序依据；人民币展示必须使用独立汇率服务，并保存汇率快照和时间。[BuyWhere MCP 文档](https://api.buywhere.ai/docs/guides/mcp)

### 6.5 推荐与解释

每次推荐至少包含：

1. 首选商品
2. 推荐理由
3. 关键证据
4. 两个以内的替代方案
5. 主要取舍
6. 原价、人民币估算价和汇率时间
7. 商户和购买链接
8. 价格、库存和信息更新时间
9. 运费、税费、配送和售后信息缺失时的提醒

推荐语言示例：

> 推荐 A：满足你的预算和降噪要求，当前价格为 USD 299，按 2026-08-15 汇率约合 ¥2,149，评分 4.8，当前有货。B 的人民币估算价低约 ¥180，但续航和评价数量较弱。汇率、价格和库存会变化，最终金额以商户页面为准。

### 6.6 价格历史与提醒

第二阶段支持：

- 查询商品近 30–90 天价格历史
- 保存商品到愿望清单
- 用户设置目标价格
- 价格下降后发送提醒

价格提醒应采用异步任务，避免每次对话都触发多个 API 请求。

### 6.7 异常处理

系统需要处理：

- API Key 无效：提示服务配置问题，不泄露密钥。
- 参数错误：解释缺失或冲突的搜索条件。
- 无结果：放宽软条件，但不能自动放宽硬条件。
- 429 限流：读取 `Retry-After`，使用指数退避并展示服务降级状态。
- 商品详情不存在：保留搜索结果并标记详情不可用。
- 价格或库存过期：降低可信度，并提示用户在商户页面确认。
- BuyWhere 服务异常：返回已有缓存或明确说明当前无法完成实时检索。

## 7. Agent 架构要求

### 7.1 逻辑分层

```text
交互层
  └─ 对话、结果卡片、比较视图、购买跳转

Agent 编排层
  └─ 意图解析、追问、任务规划、会话状态

决策层
  └─ 硬约束过滤、规格比较、去重、人民币换算、排序、解释生成

货币与成本层
  └─ 汇率快照、人民币换算、已知运费/税费、价格置信度

数据接入层
  └─ BuyWhere REST/MCP Adapter、缓存、重试、限流、契约校验

证据与观测层
  └─ 商品快照、请求日志、推荐理由、数据更新时间、错误追踪
```

### 7.2 Agent 设计原则

- LLM 负责理解用户意图和生成解释，不负责编造商品事实。
- 商品价格、库存、商户和规格必须来自工具结果或缓存快照。
- 硬约束判断使用确定性代码，不能完全交给模型。
- 人民币价格必须由独立汇率模块计算，不能让 LLM 心算或猜测汇率。
- 每个推荐结论必须能追溯到商品 ID和原始字段。
- 生产环境优先使用后端 REST Adapter；MCP 用于原型和工具化接入。[官方 MCP 集成指南](https://api.buywhere.ai/docs/guides/mcp)
- API Key 只存储在服务端，不能放入浏览器代码。BuyWhere 文档明确指出浏览器直连会暴露 API Key。[官方 MCP 集成指南](https://api.buywhere.ai/docs/guides/mcp)

### 7.3 推荐排序建议

排序顺序：

1. 先过滤预算、国家、规格等硬条件。
2. 将不同平台的原始价格转换为人民币估算价，并标记汇率时间。
3. 再计算人民币价格价值、规格匹配、评分、评价数量、库存和数据新鲜度。
4. 最后结合用户偏好生成推荐理由。

建议至少输出以下内部评分字段：

- `constraint_match_score`
- `rmb_price_value_score`
- `fx_confidence_score`
- `landed_cost_completeness_score`
- `spec_match_score`
- `trust_signal_score`
- `freshness_score`
- `overall_score`

## 8. MVP 范围与优先级

### P0：必须完成

- 中文/英文多轮购物对话
- 人民币预算、目标国家、目标平台、原币种和商品规格解析
- 多市场、多平台并行商品搜索
- 人民币统一换算和跨平台价格排序
- 原价、人民币估算价、汇率时间和价格置信度展示
- 候选商品去重和硬约束过滤
- 3–5 个候选商品的结构化比较
- 首选和备选推荐
- 推荐理由与证据字段
- 商品详情和商户购买链接
- API 超时、限流、无结果和鉴权错误处理
- 服务端 API Key 管理
- 汇率服务异常时的降级处理和原币种展示
- 请求日志和推荐追踪

### P1：上线后增强

- 商品价格历史
- 愿望清单
- 人民币目标价格提醒
- 用户偏好记忆
- 运费、税费和配送时效接口
- 商户可信度和售后信息

### P2：长期方向

- 多代理协作选品
- 用户授权后的购物车和下单协助
- 自动化订单追踪
- 个性化长期购物画像
- 商户或品牌侧的 Agent 采购服务

## 9. 非功能需求

### 性能

- 首次搜索目标响应时间：P95 不超过 3 秒。
- 已缓存搜索目标响应时间：P95 不超过 1 秒。
- 单次对话默认只触发必要的 API 请求，避免无控制的工具循环。
- 汇率缓存命中时不增加明显的用户感知延迟。
- 支持 BuyWhere 免费额度进行开发测试，并为生产环境预留更高额度。

BuyWhere 公开资料中给出的速率限制包括免费层 60 RPM、生产层 600 RPM；正式上线前需要用实际 API Key 再次确认配额。[BuyWhere MCP 文档](https://api.buywhere.ai/docs/guides/mcp)

### 安全

- API Key 仅存在于后端环境变量或密钥管理系统。
- 日志中不得记录完整 API Key、用户支付信息或不必要的个人信息。
- 对用户输入进行长度、参数和提示注入防护。
- 所有购买跳转都显示真实商户域名。
- 不在没有证据时宣称商品正品、可配送或可退货。

### 可观测性

每次推荐至少记录：

- 用户意图摘要
- 实际搜索参数
- BuyWhere 请求状态、耗时、缓存状态
- 候选商品 ID
- 过滤原因
- 最终排序原因
- 返回给用户的证据

## 10. 成功指标

### 产品指标

- 首次对话完成率 ≥ 70%。
- 用户从首次输入到获得首轮推荐的平均追问次数 ≤ 2 次。
- 推荐结果点击商户链接率 ≥ 15%。
- 用户主动发起比较或继续追问的比例 ≥ 30%。

### 质量指标

- 硬约束违反率 < 3%。
- 推荐商品字段可追溯率 100%。
- 人民币价格展示必须同时具备原价、汇率时间和换算依据，覆盖率 100%。
- 价格、库存和商户信息的无依据陈述率为 0。
- BuyWhere API 错误能够被正确分类和降级处理，覆盖率 100%。
- 用户对“推荐理由清晰度”的评价 ≥ 4/5。

### 技术指标

- 搜索 Adapter 契约测试覆盖主要响应形态。
- 429、401、404、超时和空结果均有自动化测试。
- 推荐链路具备完整 trace，可复现同一商品候选集和排序结果。

## 11. 风险与应对

| 风险 | 概率 | 影响 | 应对策略 |
|---|---|---|---|
| BuyWhere 公开文档存在路径、字段和规模差异 | 高 | 高 | 建立 Adapter、契约测试和真实 API 冒烟测试，不让 LLM 直接依赖原始响应 |
| 商品规格并非真正同款 | 高 | 高 | 结合品牌、型号、容量、颜色和结构化规格进行同款识别 |
| 汇率变化导致人民币价格排序变化 | 高 | 中 | 使用带时间戳的汇率快照，标记估算价，定期刷新并允许按原币种查看 |
| 不同平台的价格不包含相同费用 | 高 | 高 | 区分商品价、已知总价和最终到手价，不把商品人民币估算价称为最终价格 |
| 价格或库存过期 | 中 | 高 | 展示 `updated_at`，检查缓存状态，购买前要求用户确认商户页面 |
| 缺少运费、关税、退货和保修信息 | 高 | 高 | MVP 明确限制，后续接入物流、税费和商户政策数据 |
| API 限流或服务不可用 | 中 | 中 | 缓存、指数退避、请求预算、降级响应和监控 |
| 模型为了给出完整答案而补充不存在的信息 | 中 | 高 | 证据绑定、结构化输出、事实字段白名单和幻觉评估 |
| 用户认为“推荐”就是价格最低 | 中 | 中 | 明确展示综合排序维度和候选商品取舍 |

## 12. 开发前验证清单

1. 使用真实 API Key 验证 `/v1/products/search` 的实际路径和返回字段。
2. 分别测试多个 `country_code`、`currency`、`compact=true`、`limit` 和无结果场景。
3. 验证响应究竟使用 `data` 还是 `items`，并在 Adapter 中统一。
4. 验证商品 ID 是否可以用于详情、比较和价格历史接口。
5. 验证价格历史是否包含足够数据，不把缺失历史解释成稳定价格。
6. 验证 401、404、429、超时和空结果的真实响应格式。
7. 确认 API Key 配额、商业使用许可、归因要求和购买链接规则。
8. 确认各目标平台的商品价、运费、税费和配送数据是否可获得。
9. 选择一个品类完成 30–50 个真实购物问题的离线评估集，并覆盖至少 3 个市场或平台。

## 13. 结论

InteRecAgent 的核心价值不是替 BuyWhere 做商品搜索，而是在 BuyWhere 的结构化商品数据之上增加：

- 对用户意图的理解
- 跨国际平台和跨市场的候选聚合
- 人民币统一换算与价格排序
- 跨市场和跨商户的约束处理
- 商品规格和同款判断
- 可解释的综合决策
- 价格与数据新鲜度意识
- 面向用户的风险披露

因此，项目应被定义为“跨平台跨境商品推荐 Agent”，而不是“单一平台搜索工具”“电商搜索聊天机器人”或“自动代购系统”。首个可交付版本应围绕“理解人民币预算 → 聚合国际平台候选 → 统一换算比价 → 比较取舍 → 给出证据化推荐 → 跳转购买”这一闭环完成验证。
